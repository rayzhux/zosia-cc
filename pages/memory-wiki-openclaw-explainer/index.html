01

Why this exists

Your dog-sitter example is exactly the bug. prose memory is append-only, but belief state is not. old statements linger, newer ones conflict, and the model is left to guess which line wins.

The problem

Plain notes have no stable overwrite model

Three different feeding instructions can all remain in the file. The newest one should win, but the file itself does not encode that relationship.

What wiki changes

Beliefs become named claims, not loose sentences

A claim can be current, contested, stale, low-confidence, or unresolved. That means the system can reason about the belief layer instead of re-reading prose every turn.

Why it matters

You get truth maintenance, not just more storage

That is the real upgrade. memory-wiki is not about more notes. It is about keeping the knowledge layer internally coherent.

03

What memory-wiki actually adds

Vault structure

Deterministic pages, not random note sprawl

  • WIKI.md vault guide
  • index.md top-level map
  • entities/ people, projects, systems
  • concepts/ ideas, policies, patterns
  • syntheses/ compiled summaries
  • sources/ raw imported material
  • reports/ health dashboards
  • .openclaw-wiki/cache/ agent-digest.json, claims.jsonl
Structured belief model

Claims and evidence become first-class

  • Claims can carry id, text, status, confidence, and updatedAt.
  • Evidence can point to source ids, file paths, line ranges, notes, and weights.
  • The compiler can then rank, contest, or surface gaps instead of pretending all prose is equally valid.
Tools

wiki_search / wiki_get

Search and read the compiled vault directly when provenance and page identity matter.

Safe mutation

wiki_apply

Update syntheses or metadata without freehand surgery in generated sections.

Health checks

wiki_lint

Find contradictions, stale pages, low-confidence claims, open questions, and provenance gaps.

Dashboards

reports/*.md

Built-in outputs include contradictions, stale pages, claim health, low confidence, and open questions.

04

Modes and tradeoffs

There are three vault modes. Only two are sane for normal use.

Mode Best for Pros Cons My recommendation
isolated Starting clean, low blast radius Own vault, predictable behavior, no dependency on memory-core internals Does not automatically compile every existing memory artifact Start here
bridge Organizing exported artifacts from the active memory plugin Can ingest daily notes, memory root files, dream reports, memory events More coupled, and value depends on what the active memory plugin exports publicly Good phase 2
unsafe-local Weird local edge cases Direct same-machine escape hatch Non-portable, easy to get cursed Do not start here

My recommendation for your setup: use isolated first. You already have LCM for chat continuity and memory-core for recall. Start with the cleanest wiki layer possible, prove the dashboards are useful, then consider bridge if you want broader automatic ingestion from existing memory artifacts.

06

The config I would actually use

This keeps the rollout conservative: isolated vault, dashboards on, shared search backend, no compiled digest injected into prompts yet.

~/.openclaw/openclaw.json recommended patch 
{
  "plugins": {
    "allow": [
      "device-pair",
      "discord",
      "memory-core",
      "phone-control",
      "talk-voice",
      "telegram",
      "voice-call",
      "slack",
      "lossless-claw",
      "google",
      "acpx",
      "whatsapp",
      "browser",
      "openclaw-weixin",
      "openai",
      "kimi",
      "openrouter",
      "memory-wiki",
      "wiki"
    ],
    "entries": {
      "memory-wiki": {
        "enabled": true,
        "config": {
          "vaultMode": "isolated",
          "vault": {
            "path": "~/.openclaw/wiki/main",
            "renderMode": "native"
          },
          "ingest": {
            "autoCompile": true,
            "maxConcurrentJobs": 1,
            "allowUrlIngest": true
          },
          "search": {
            "backend": "shared",
            "corpus": "wiki"
          },
          "context": {
            "includeCompiledDigestPrompt": false
          },
          "render": {
            "preserveHumanBlocks": true,
            "createBacklinks": true,
            "createDashboards": true
          }
        }
      }
    }
  }
}
Why this config

Low-risk first pass

  • vaultMode: isolated keeps the trust boundary clean.
  • render.createDashboards: true gives you the real payoff, contradiction and staleness reports.
  • includeCompiledDigestPrompt: false avoids changing prompt shape until we see the vault is useful.
What I would delay

Bridge mode and prompt injection

  • Bridge mode is worth testing later, not on minute one.
  • Compiled digest prompt injection is useful, but I would only turn it on after the wiki pages are healthy.
  • Obsidian mode is optional. Native mode is simpler unless you specifically want Obsidian workflows.
07

How we enable it, step by step

Edit ~/.openclaw/openclaw.json

Add the memory-wiki entry under plugins.entries, then add memory-wiki and wiki to plugins.allow.

Restart the gateway cleanly

Use openclaw gateway restart. Do not stop the gateway. Restart is the safe path here.

Initialize the vault

Run openclaw wiki init. This creates the vault layout and starter pages under ~/.openclaw/wiki/main.

Compile it immediately

Run openclaw wiki compile to generate the machine-readable digest files and any dashboard pages.

Lint before trusting it

Run openclaw wiki lint. That is the moment where contradictions, stale pages, low-confidence claims, and open questions become visible instead of silently rotting.

Use the right retrieval path

For broad recall, keep using memory search. For provenance-heavy belief checks, use wiki_search and wiki_get.

My strong opinion: this is worth enabling. LCM solved “don’t lose the conversation.” memory-wiki solves “don’t let durable memory quietly contradict itself.” Those are different problems, and this one is finally aimed at the second.
