Reference

Every Session Knob, Explained

1. Session Reset session.reset

Controls when a session gets wiped and starts fresh. Two modes, can combine both (first to fire wins).

ModeHow It WorksBest For
daily Resets at atHour local time (default 4 AM). Next message after that hour starts a new session. Predictable "fresh start" each day. Good for cron-heavy setups or shared bots.
idle Resets after idleMinutes of no activity. Timer resets on every message. Conversations that span days but shouldn't live forever. Your current setup.
Both Set both mode fields + atHour + idleMinutes. Whichever expires first wins. Belt-and-suspenders: idle catches long gaps, daily catches never-ending sessions.

2. Reset By Type session.resetByType

Per-context-type overrides for the reset policy. Types: direct (DMs), group (group chats), thread (Discord/Slack threads). Each can have its own mode, atHour, and idleMinutes.

Why it matters: DMs with you are long-running chief-of-staff conversations — they deserve long idle windows. A Telegram group or Slack thread is task-scoped and shouldn't hold stale context for a week.

3. DM Scope session.dmScope

How DMs are bucketed into sessions.

ValueIsolationWhen to Use
mainAll DMs share one sessionSolo user, wants continuity across all channels
per-peerBy sender ID (cross-channel)Multi-user, same person across channels shares context
per-channel-peerBy channel + senderMulti-user or multi-channel privacy. Your current, correct choice.
per-account-channel-peerBy account + channel + senderMulti-account setups (multiple bot accounts per channel)

4. Thread Bindings session.threadBindings

Controls bound thread sessions (Discord/Slack threads that maintain their own session).

  • enabled — master switch for thread-bound sessions
  • idleHours — auto-unfocus (drop binding) after N hours of inactivity. 0 = never auto-unfocus.
  • maxAgeHours — hard cap regardless of activity. 0 = no max age.

Discord can override these via channels.discord.threadBindings. Your Discord config already has spawnAcpSessions: true.

5. Session Maintenance session.maintenance

Automatic cleanup of the session store and transcript files. You don't have this set — sessions accumulate indefinitely.

  • mode — "warn" (log only) or "enforce" (actually delete)
  • pruneAfter — age cutoff for stale entries (default 30d)
  • maxEntries — cap on sessions.json entries (default 500)
  • rotateBytes — rotate sessions.json when it exceeds this size (default 10mb)
  • resetArchiveRetention — how long to keep *.reset.* transcript archives. Defaults to pruneAfter; false disables.
  • maxDiskBytes — optional hard budget for the sessions directory
  • highWaterBytes — target after cleanup (default 80% of maxDiskBytes)

6. Parent Fork Guard session.parentForkMaxTokens

When a new thread inherits from a parent session, skip the fork if the parent has more than N tokens. Starts a fresh thread session instead. Default: 100000. Set 0 to always allow forking.

Prevents massive parent transcripts from being duplicated into every thread spawn.

7. Context Pipeline Compaction + Pruning + LCM

Three complementary systems that manage what the model sees:

SystemWhat It DoesPersistent?Your Setting
Pruning Trims old tool results (exec output, file reads) from in-memory context No — per-request only cache-ttl / 3h
Compaction Summarizes older conversation into a compact entry in the transcript Yes — saved to transcript safeguard
LCM DAG-based context engine — nothing truly lost. Agent can search/expand old context via lcm_grep/lcm_expand Yes — owns compaction lossless-claw ✓

LCM owns compaction when active, meaning it replaces the legacy summarizer with its DAG approach. The pruning and compaction settings still matter as fallback/guard behaviors.

Changes

What Changes and Why

NEW resetByType — differentiated expiry

DMs → 7 days idle. Your main interaction. You pick up conversations after weekends, travel days. LCM handles the context — long sessions are fine.

Groups → 24 hours idle. Telegram group, any shared chat. Task-scoped conversations that shouldn't carry a week of stale context. 24h is generous enough for a multi-day group discussion but clears out dead ones.

Threads → 48 hours idle. Discord/Slack threads are task-specific. 48h lets you pick up a thread the next day, but doesn't keep a week-old debug thread alive in memory.

CHANGED threadBindings — tighter but with safety net

idleHours: 168 → 72. Three days of inactivity before auto-unfocus. A thread you haven't touched in 3 days is almost certainly done. If you need it again, the LCM DAG still has all the history — you just start a fresh binding.

maxAgeHours: 0 → 336 (14 days). Hard cap. Even if a thread stays active, the binding resets after 2 weeks. This prevents unbounded transcript growth in long-running threads. LCM's searchable history means you lose nothing — the binding just starts fresh.

NEW maintenance — stop infinite accumulation

This is the most important change. Without maintenance, every session ever created lives in sessions.json and its transcript files stay on disk forever. Over months, this grows into hundreds of MBs of stale transcripts.

  • enforce mode — actually cleans up (not just warnings)
  • pruneAfter: 30d — stale session entries older than 30 days get removed
  • maxEntries: 500 — hard cap on session store entries
  • resetArchiveRetention: 14d — archived transcripts (from /new resets) kept 14 days
  • maxDiskBytes: 500mb — hard budget for the sessions directory

KEPT Everything else — already optimal

  • dmScope: per-channel-peer — correct for your multi-channel setup
  • reset.mode: idle with 10080 — stays as the global default (overridden per-type above)
  • contextPruning: cache-ttl / 3h — good for Anthropic caching costs
  • compaction.mode: safeguard — appropriate guard for LCM
  • contextEngine: lossless-claw — the whole point of the LCM investment
  • parentForkMaxTokens: 100000 — sensible guard
  • Slack thread.historyScope: thread — correct thread isolation
  • Discord spawnAcpSessions: true — needed for ACP thread spawning
Interactions

How These Systems Layer

Message arrives → routed to session by scope/dmScope
→ Session alive? Check reset (and resetByType if set) — idle timer or daily boundary
→ If expired: New session ID, old transcript archived (if resetArchiveRetention)
→ If thread: Check threadBindings.idleHours and maxAgeHours
→ Building context: LCM assembles from DAG. Pruning trims old tool results.
→ Context too big? LCM compacts (DAG summary). safeguard mode as fallback.
→ Background: maintenance periodically prunes stale session entries + transcripts from disk.

Key Nuance: LCM changes the calculus

Without LCM, shorter sessions = better context quality (less stale info in window). With LCM, session length barely matters for context quality — the DAG handles it. But it still matters for disk usage and session store hygiene. That's why maintenance mode is critical even with LCM.
