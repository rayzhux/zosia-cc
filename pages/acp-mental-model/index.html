OpenClaw / ACP / ACPX mental model

ACP is the protocol. ACPX is the transport layer. OpenClaw is the orchestrator.

This page is the shortest honest version of a messy system: how OpenClaw talks to Codex / Claude Code over ACP, what ACPX actually does, why recent releases touched it so much, and how you should think about using it in Discord and in coding workflows.

The one-line mental model
OpenClaw manages sessions, routing, history, thread bindings, permissions, and delivery. ACPX manages the ugly part: speaking ACP to external coding agents cleanly instead of scraping terminal text like an animal.
Why the last releases touched it
  • Persistent ACP session history and lineage got better.
  • Discord thread bindings for ACP got durable.
  • OpenClaw is moving toward ACP as a first-class control plane, not a hacky sidecar.
  • That matters directly for your Codex / Claude Code usage.

1 — Plain English

What ACP is

ACP = Agent Client Protocol. It is a structured protocol for one agent/client to talk to another coding agent. Think JSON events, sessions, tool calls, cancels, status, diffs — not raw terminal text.

What ACPX is

ACPX = a headless CLI client for ACP. It gives one command surface for codex, claude, gemini, opencode, pi, and custom ACP servers. It handles persistent sessions, queueing, cancel, reconnect, and structured output.

What OpenClaw does with them

OpenClaw uses ACP / ACPX so Discord, cron, agents, and tools can hand work to external coding agents in a durable, inspectable, routeable way — especially now that Discord thread bindings and ACP session persistence have matured.

The key distinction: ACP is not “another model.” ACP is the wire protocol. ACPX is not “the intelligence.” ACPX is the bridge/runtime wrapper. Codex and Claude Code are still the things doing the work.

Why OpenClaw does not just scrape PTY output
  • PTY scraping is brittle and ugly.
  • You lose structure: tool calls, diffs, thinking, status, cancel semantics.
  • Queueing and reconnect become guesswork.
  • Multi-turn persistent sessions are much cleaner over ACP.
Why OpenClaw does not make ACPX the whole system
  • OpenClaw still needs to own routing, Discord thread binding, and delivery invariants.
  • Recent design docs explicitly say ACP runtime can be pluginized, but ACP routing must still exist in core.
  • That split is why both ACP and ACPX keep showing up in release notes.

3 — There are actually three different ACP-shaped modes

Mode A

openclaw acp = OpenClaw as an ACP server/bridge

An IDE or ACP-aware client talks into OpenClaw. Docs describe this as an ACP bridge over stdio to the Gateway over WebSocket, keeping ACP sessions mapped to OpenClaw session keys.

Mode B

OpenClaw ACP runtime = OpenClaw sends work out to external coding agents

This is what matters most for your Discord/Codex/Claude setup. OpenClaw owns the control plane, then uses an ACP backend — today usually ACPX — to run Codex or Claude Code as persistent external coding sessions.

Mode C

acpx openclaw = external ACP client talks to OpenClaw

Docs also support the reverse direction: ACPX can use its built-in openclaw target so Codex/Claude-like clients can query OpenClaw for context through ACP instead of terminal scraping.

Why this is confusing

Because “ACP” is both the protocol and part of several product surfaces. In practice, for your daily use, the one that matters is Mode B: OpenClaw orchestrating Codex or Claude Code as durable ACP sessions, especially inside Discord threads.

What that means operationally

You are not merely “ACP-capable.” You are already configured for Discord-native persistent ACP coding sessions.

Discord can create/bind ACP threads Codex is your default ACP target Claude is allowed too OpenClaw owns routing ACPX is the runtime backend

So when you ask for a Codex or Claude Code thread in Discord, OpenClaw is increasingly acting like a mission-control layer, not just a bot forwarding prompts.

The architecture OpenClaw is moving toward

Design docs describe a target state where OpenClaw owns an ACP control plane: session records, run records, idempotency, durable event logs, recovery, thread bindings, and exactly-once-ish delivery rules. ACPX remains the first pluggable runtime backend. Translation: OpenClaw wants to be the system-of-record, while ACPX remains the execution transport.

6 — How you should use it

Use normal OpenClaw chat when…
  • You want advice, summaries, quick answers.
  • No external coding harness is needed.
  • You want the main agent brain, not a specialist coding runtime.
Use ACP thread sessions when…
  • You want a durable Codex or Claude Code workstream.
  • The task spans multiple turns, files, or iterations.
  • You want the thread itself to be the workspace boundary.
  • You may come back after a restart and continue.
Use direct ACP/ACPX only when…
  • You’re wiring an IDE or another ACP-aware client directly.
  • You want low-level harness control or debugging.
  • You’re testing the protocol, not just delegating work.
Recommended working model for you
Think of Discord threads as named coding lanes. OpenClaw is the air-traffic controller. Codex / Claude Code are the aircraft. ACP is the radio protocol. ACPX is the radio stack.
Practical rule of thumb
  • Codex thread for building / editing / shipping code.
  • Claude Code thread when you want a different coding harness or style.
  • Main OpenClaw chat for orchestration, synthesis, planning, and cross-system work.
  • Don’t confuse model selection with ACP runtime selection — they solve different problems.
Final opinion

ACP / ACPX matter to you because they turn OpenClaw from “chatbot with tools” into “control plane for external coding agents.” If you embrace that framing, the product starts to make a lot more sense: Discord is not just where you talk — it becomes where you operate long-lived coding workstreams.
