Final Recommendation

The Config to Apply

Turn on Docker sandbox for all non-main sessions. Your private DM stays full-access. Everything else — group chats, channels, public sessions — runs tools inside a throwaway container.

openclaw.json patch
{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "non-main",
        "scope": "session",
        "workspaceAccess": "none",
        "docker": {
          "network": "bridge"
        }
      }
    },
    "list": [
      {
        "id": "main",
        "default": true,
        "sandbox": { "mode": "off" }
      }
    ]
  }
}

Then build the sandbox image once: scripts/sandbox-setup.sh

Why These Specific Settings

mode: "non-main"

Your private DM is your trusted lane — no friction. Group chats, channel sessions, and public contexts get sandboxed automatically. The session class is the trigger, not AI judgment about "is this risky."

scope: "session"

One container per conversation. Each session is isolated from every other session. shared reuses one container for everything — that's how cross-task contamination sneaks in.

workspaceAccess: "none"

The sandbox gets its own empty workspace. Your host filesystem, secrets, and config stay invisible. Upgrade to "ro" for code review or "rw" for edits — only when the task demands it.

network: "bridge"

Standard Docker networking — the agent can reach the internet for research, docs, APIs. The main threat is the model doing something dumb to your filesystem, not sophisticated data exfiltration from yourself.

The 3 Security Levers

OpenClaw splits security into three independent controls. Understanding each one matters — sandbox alone isn't the full picture.

Lever What It Controls Config Path Default
Sandbox Where tools run — Docker container vs host agents.defaults.sandbox.* off
Tool Policy Which tools are even callable — allow/deny lists tools.allow / tools.deny all allowed
Elevated Exec-only escape hatch back to host tools.elevated.* off

Key insight: Sandbox on + broad tool policy + elevated enabled = sandboxing theater. Lock down tool policy and keep elevated as break-glass, not daily driver.

The Network Question

Why bridge (full internet) and not none

The default Docker sandbox has no network. That sounds secure, but it breaks every real task — research, browsing, API calls, docs, package installs. Three real patterns exist:

Pattern Network Blocks Exfiltration? Supports Research? Complexity
No network none Yes No Trivial
Egress proxy
Squid or Docker Sandboxes proxy		 Allowlisted hosts only Yes Yes (allowed hosts) Medium — needs proxy setup
Bridge (recommended) bridge No Yes Trivial

For a single-user personal gateway, bridge is the right default. Your threat model is "model does something dumb to the filesystem" — not a nation-state exfiltrating data from a sandboxed container. Egress proxy is the upgrade path if you later expose the gateway to untrusted users.

Agent exfiltrates data to the internet No (with bridge) Needs egress proxy to block; low risk for single-user
Upgrade Paths (If You Need More)

Egress Proxy

Route sandbox traffic through Squid or Docker's Sandboxes proxy. Allowlist only the hosts your tasks need (API providers, GitHub, Reddit). Blocks exfiltration while keeping research working.

When: You expose the gateway to untrusted users or handle sensitive data in sandbox sessions.

Multi-Agent Split

Create separate agents with different security profiles: research (sandboxed + network), code-review (sandboxed + read-only workspace), public (sandboxed + restricted tools).

When: Different task types genuinely need different trust boundaries.

MicroVM / gVisor

Replace Docker namespacing with gVisor (runsc) or Firecracker MicroVMs for kernel-level isolation. Each session gets its own kernel — cross-session kernel exploits become structurally impossible.

When: Running untrusted agent-generated code in production or handling truly adversarial inputs.

Separate Gateway / VM

Run personal and public gateways on different hosts or VMs. Machine-level boundary is the strongest isolation. Docker sandbox on top of that is defense-in-depth.

When: Serious multi-user setup or enterprise-grade exposure requirements.

What Not to Do

Anti-Patterns

  • scope: "shared" — one container for everything. Cross-session contamination risk. Use "session".
  • workspaceAccess: "rw" as default — mounts your real filesystem into every sandbox. Defeats the purpose.
  • Normalized elevated mode — elevated is the "break glass" button. If every session uses it, the host is always on the table.
  • Letting the model decide "is this risky?" — deterministic routing by session type beats AI judgment. Session boundaries are the trigger.
  • Mounting Docker socket into sandbox — gives the container control over the host. The docs explicitly block this.
  • Mounting /etc, .ssh, secrets paths — binds pierce the sandbox. Only mount what the task specifically needs, read-only.

The Bottom Line

Flip sandbox.mode from "off" to "non-main" with bridge network. That single change gives you filesystem isolation on every non-private session with zero friction on your main workflow. It's the highest-value security improvement you can make today, and it takes one config patch to apply.

Upgrade to egress proxy, multi-agent splits, or MicroVMs later — only when your threat model actually calls for it.
