🔴 Critical Issues

1. #sys-security has requireMention: false but system prompt says "Only respond when @mentioned"

This channel (the one you're asking from) has requireMention: false, so I receive every message. But the system prompt tells me to only respond when @mentioned. This creates a conflict — I see the message, process it, but the system prompt tells me to stay quiet. Result: I consume tokens silently doing nothing, or respond inconsistently.

Same problem in: #sys-heartbeat, #sys-token-usage, #sys-backups, #health, #daily-news — all have requireMention: false but their system prompts say "only respond when @mentioned."

✅ Fix: Set requireMention: true on all automated/output-only channels. Reserve requireMention: false only for channels where you want me to respond to every message.
2. #sys-fixes is missing requireMention entirely

Channel C0AQCJKR37G (#sys-fixes) has no requireMention set. It inherits from the wildcard * rule which is requireMention: true. So you'd need to @mention me there to get a response, even though it's meant to be a primary responder channel for troubleshooting.

✅ Fix: Add requireMention: false to the #sys-fixes channel config.
3. replyToMode: "first" forces all channel replies into threads

With replyToModeByChatType.channel: "first", every response I send in a channel goes as a threaded reply to the first message. This means:

  • Top-level messages from me in channels are impossible — everything becomes a thread reply
  • Cron output (daily brief, security reviews, health reports) that should appear as top-level posts gets buried in threads
  • If two conversations happen in the same session, the second reply threads under the first message — wrong thread

This is likely the "messages went to wrong channels" issue you're seeing — it's actually messages going to wrong threads.

✅ Fix: Consider replyToModeByChatType.channel: "off" for channels (lets cron posts be top-level), or keep "first" only for interactive channels like #daily and #sys-fixes.
4. requireMention: false on ~14 channels creates massive token waste

Every message in 14 channels triggers a full agent session. Most of these are bot output channels (heartbeat, backups, token usage, security) where I shouldn't respond unless asked. Each silent processing round costs tokens and can delay interactive responses due to concurrency limits.

✅ Fix: Flip to requireMention: true on all output-only channels. Only keep false on #daily, #intel, #sys-fixes, #development, #alerts.

🟡 Warnings

5. DM replyToMode: "off" — explicit reply tags don't work in Slack DMs

Unlike Telegram where "off" still honors explicit [[reply_to_*]] tags, Slack's "off" disables all reply threading — including explicit tags. This means DM conversations can't use threaded context.

✅ Fix: If you want DM threading, change to "first". If flat DMs are intended, this is fine as-is.
6. thread.inheritParent: true may cause context bleeding

Currently set to true, which means thread sessions inherit the parent channel session's context. Combined with the replyToMode: "first" threading, this can create confused context when multiple threads are active.

✅ Fix: Set thread.inheritParent: false (the documented default) unless you specifically want thread context inheritance.
7. No channels.slack.accounts.default.channels override — routing uses top-level only

Channel routing config lives at channels.slack.channels but the default account doesn't have its own channel overrides. This works fine for now but means both Zosia and Argus use the same channel routing (Argus uses its own account-level requireMention: true wildcard to stay quiet).

ℹ️ Not broken, just something to know. Current Argus isolation via account-level requireMention: true works.
8. userTokenReadOnly: false at top level but true at account level

Top-level config has userTokenReadOnly: false, but both accounts.default and accounts.argus have userTokenReadOnly: true. Account-level should win, but this discrepancy could cause confusion during troubleshooting.

✅ Fix: Align top-level to true to match account configs, or remove the top-level key.
9. WhatsApp is disconnected (separate issue, not Slack)
