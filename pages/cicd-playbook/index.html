The pushback you need to hear

"I won't write code" is fine — plenty of successful products are built that way now. "I'll trust AI to maximum" is where it gets dangerous. AI can build, review, and fix. It should not approve itself, deploy itself, and declare itself healthy. That's not leverage. That's an unsupervised loop with your production database inside it.

01

Your operating model

Control plane

Linear is the work queue

Every piece of work starts as a Linear issue with a problem statement, acceptance criteria, and non-goals. AI builds from specs, not vibes. If the issue is vague, the PR will be vague.

Execution plane

AI handles all implementation

One issue → one branch → one PR. Small diffs let reviewers be sharp, previews be fast, and rollback be painless. Giant cross-cutting PRs are where AI-native projects die.

Truth plane

CI + Sentry decide reality

Tests, type checks, preview deploys, and production telemetry are the external truth layer. They exist because AI can write code that passes its own review but breaks in production.

Your job isn't coding anymore. It's owning the quality bar: branch protections, deploy policy, rollback rules, and the definition of "green enough to ship."

CI, AI review, preview deploy, fix loops — all here.

Step 4

Auto-merge after all required checks pass.

Step 5

Deploy from main

Production has one canonical source. Always.

Antipatterns
  • A permanent dev branch "because real teams use them"
  • Direct pushes to main — even "quick fixes"
  • Production deploys from feature branches
  • Mega-PRs touching auth, DB schema, and UI in one diff
  • AI reviewing + approving + deploying its own work in a closed loop
What to do instead
  • Short-lived feature branches, killed after merge
  • PR is the single place where all quality work happens
  • Protected main is always in a deployable state
  • Small PRs, fast merges, visible previews, clean rollback boundaries
  • External truth layer (CI + Sentry) that AI can't override
03

Hard gates vs soft gates

If a check is objective and deterministic, make it block merges. If it's interpretive, keep it advisory. Three bots arguing about variable naming while a broken migration slides through is the exact failure mode you're trying to avoid.

CheckWhat it catchesGate type
Lint + formatStyle drift, dead imports, obvious mistakes — before anyone wastes review time.required
TypecheckBroken signatures, invalid imports, contract violations.required
TestsBehavioral correctness. At minimum: a smoke path for the critical user journey.required
BuildWhether the deploy artifact actually compiles and packages.required
Preview deployThe running app on a real URL. Catches UI/integration problems that tests miss.required for ui apps
AI reviewSuspicious logic, missing tests, security patterns, maintainability risks.advisory
SAST / dep scanKnown CVEs, dangerous patterns. Useful but noisy if not tuned.advisory by default
Prod approvalHuman pause before production. Worth it only when blast radius is real.context-dependent
The rule: deterministic checks block. AI advises. If you let AI block on subjective style opinions, you'll spend more time managing the bot than managing the product.
04

AI reviewer roles

One always-on reviewer. Two specialists invoked when needed. If all three pile onto every PR, you get duplicate comments, inconsistent severity, and attention fatigue. Keep the signal clean.

Always on

CodeRabbit

Default PR reviewer. Built for continuous review and planning. Comments on every PR automatically. This is your first line of AI review — reliable, configurable, and doesn't need prompting.

On demand

Codex

Invoke for security regressions, architecture scrutiny, and autonomous CI-fix loops. Best at: "this PR touches auth — give it a deep security pass" or "CI is red, fix it."

On demand

Claude

Invoke for issue-to-PR generation, implementation critique, and tricky repo-context reasoning. Best at: "turn this Linear issue into a working PR" or "review this migration for backward compat."

Give them context

Repository instructions

  • Keep a top-level AGENTS.md with review guidance.
  • Specify what matters in this repo: auth rules, PII policy, perf budgets, migration constraints.
  • Tell reviewers what to ignore: docs typos, generated files, subjective renames.
  • Link AI work to Linear issue IDs and acceptance criteria.
Don't let them

Unsupervised dangerous ops

  • Approve their own deployment workflow changes.
  • Change secret handling without human scrutiny.
  • Ship giant cross-cutting PRs with no preview and no rollback plan.
  • Declare production healthy based only on their own review passing.
Why not make AI review a hard gate?
You can — but only if the tool lets you scope severity. Making CodeRabbit block on every comment means it can hold up a PR over a naming suggestion. The better pattern: let AI flag critical/security findings as blocking, and keep everything else advisory. Most teams that start with "AI blocks all PRs" end up turning it off within a month because the false-positive rate is exhausting.

Deploy + observe

Environment model

Every PR

Preview

Vercel/Railway preview URL. Shareable. Optional smoke/E2E against it.

Merge to main

Production

Deploy only from protected main. Manual approval only when blast radius demands it.

Default for you: preview every PR, auto-deploy prod on merge. Don't build a staging environment unless you actually need release batching or stakeholder signoff.

Observability loop

  • Sentry from day one. Front-end and back-end exceptions, before the first real user shows up.
  • Release tags on every production deploy so stack traces map to shipped commits.
  • Uptime / health checks for critical endpoints and scheduled jobs.
  • Regression intake back into Linear — AI picks up new bugs as work items automatically.
  • Product analytics only where it sharpens roadmap or bug triage. Don't track for tracking's sake.

Git policy

Protect main hard

Require PRs, required checks, conversation resolution. Use GitHub rulesets over legacy branch protection — cleaner policy management.

Workflow policy

Treat CI as prod infra

Minimal token permissions, pinned action SHAs where practical. .github/workflows/** changes get extra scrutiny.

Delivery policy

Small PRs or nothing

If a PR touches auth, payments, infra, and UI all at once — split it. You're not proving bravery. You're making rollback impossible.

07

30-day rollout

Week 1 — Foundation
Wire the safety rails
Protect main with rulesets. Set up lint/typecheck/test/build as required checks. Connect Vercel or Railway for preview deploys. Install Sentry. Write your repo's AGENTS.md with review instructions for AI.
Week 2 — AI work loops
Close the Linear → PR loop
Set up Linear → branch → PR automation. Enable CodeRabbit as default reviewer. Configure @codex and @claude comment triggers for specialist review. Test the full cycle: issue → AI branch → PR → CI → review → merge → deploy.
Weeks 3–4 — Tighten
Close the production feedback loop
Add smoke tests on preview URLs. Enable Sentry release tagging on deploy. Set up regression-to-Linear intake so AI auto-picks up prod bugs. Add manual prod approval only if your app handles auth, payments, or user data that would be costly to break.
If you do only three things first: protect main, get preview deploys on every PR, and install Sentry before your first real user shows up. Those three buy you an absurd amount of sanity for about an hour of setup.
What about the Linear → AI automation specifically?
Symphony (OpenAI) and similar tools are emerging for Linear → agent orchestration. The pattern: a webhook fires when a Linear issue moves to "Ready for Dev," an agent picks it up, creates a branch, writes code, opens a PR, and links it back to the issue. You've already looked at this — the key is making sure the PR still goes through the full CI + review flow, not a shortcut path. The automation is in the creation of work, not the approval of work.
