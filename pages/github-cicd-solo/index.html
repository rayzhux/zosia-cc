AI-native delivery blueprint · GitHub + Linear + previews + observability

Final recommended setup for your one-man AI software factory

The right shape is Linear issue → AI feature branch → PR → deterministic CI + AI review → preview deploy → merge to protected main → production deploy → Sentry/monitoring feedback → new AI fix PRs. AI does almost all the building; GitHub rules, environments, and observability stop it from shipping nonsense at 2am.

My blunt take

You can absolutely choose to never write code yourself. That part is fine. The part I’d push back on is letting AI review itself, approve itself, deploy itself, and declare itself healthy with no external truth layer. That’s not leverage — that’s automation theater with a knife in it.

01

Core operating model

This is the clean solo-builder version of modern CI/CD: trunk-based development, small PRs, preview deployments, aggressive automation, and tight release controls. Your actual job stops being “coding” and becomes specifying, constraining, approving, and reading production truth.

Control plane
Linear is the work queue
Each issue carries problem statement, acceptance criteria, non-goals, rollout notes, and observability expectations. AI should not invent product scope from vibes.
Execution plane
AI handles implementation
One issue, one branch, one PR. Small diffs make AI reviewers sharper, previews faster, and rollback less miserable.
Truth plane
CI + environments + Sentry decide reality
Tests can be wrong, reviewers can hallucinate, previews can still be flaky — but prod telemetry gives you the final vote.
Operator rule: you are not the coder anymore; you are the quality bar owner. That means branch protection, secrets hygiene, rollout rules, rollback rules, and the definition of “green enough to ship” are on you.

Don’t do this
  • Use a permanent dev branch just because “teams do that.”
  • Let random direct pushes hit main.
  • Trigger production deploys from feature branches.
  • Allow giant AI PRs touching ten systems at once.
Do this instead
  • Short-lived feature branches only.
  • PR is the center of review, checks, previews, and fix loops.
  • main is protected and deployable at all times.
  • Small PRs, fast merges, visible previews, reversible rollouts.
03

Hard gates vs soft gates

This is the big distinction. If a thing is objective, automate it as a required status check. If a thing is fuzzy, keep it advisory. You’ll save yourself a lot of bot melodrama.

Layer Mechanism What it should do Status
Lint / format GitHub Actions Catch style drift and obvious mistakes before humans or bots waste time reviewing. hard gate
Typecheck GitHub Actions Block broken signatures, invalid imports, bad contracts. hard gate
Tests Unit / integration / smoke Confirm behavior, not just syntax. At minimum: smoke path for critical user journey. hard gate
Build CI build step Make sure deploy artifacts actually compile and package. hard gate
Preview deployment Vercel / Railway preview Render the real app so UI and integration weirdness shows up before merge. hard gate for UI-heavy apps
AI review CodeRabbit / Codex / Claude Spot risks, missing tests, suspicious logic, security regressions, maintainability problems. soft gate by default
SAST / dependency scan CodeQL / Dependabot / vendor tool Flag known vulns and dangerous patterns without relying on taste. hard only for serious repos
Prod approval GitHub Environment rule Add a human pause only when blast radius justifies it. context dependent
Simple rule: if it can be judged by a machine with low ambiguity, let it block merges. If it’s interpretive, let it advise. Otherwise you end up with three bots bikeshedding naming while a broken deploy slips through.
04

AI role split

Always-on reviewer
CodeRabbit
Make this the default PR reviewer because it’s built for continuous review and planning. One always-on reviewer is enough.
Specialist reviewer
Codex
Use on-demand for security regressions, architecture scrutiny, and “fix the CI failures” loops on PRs.
Specialist builder / critic
Claude
Use for issue-to-PR generation, implementation critique, and repo-context reasoning when the diff gets tricky.

Repository instructions they should all follow

  • Keep a top-level AGENTS.md or equivalent review guidance file.
  • Specify what matters in this repo: auth boundaries, PII rules, migration rules, performance budgets.
  • Tell reviewers what not to waste time on: docs typos, subjective renames, generated files.
  • Link AI work back to Linear issue IDs and acceptance criteria.

What not to let them do alone

  • Approve their own risky prod rollout policy changes.
  • Rewrite deployment workflows casually.
  • Change secret handling without explicit scrutiny.
  • Ship giant cross-cutting PRs with no preview, no smoke path, and no rollback note.
AI review doctrine
Use one default voice and two invoked specialists. If CodeRabbit, Codex, and Claude all pile onto every single PR, you won’t get wisdom — you’ll get duplicate comments, inconsistent severity, and attention fatigue. Keep the signal clean.
05

Deploy, environments, and observability

Environment model

PR environment
Preview
Vercel preview or Railway preview for every PR. Shareable URL. Optional smoke/E2E on that URL.
→
Main environment
Production
Deploy only from protected main. Add manual approval only when blast radius demands it.
Default for you: preview on every PR, production on merge to main. Don’t overcomplicate staging unless you really need release batching or stakeholder signoff.

Observability loop

  • Sentry from day one for front-end and back-end exceptions.
  • Release tagging on every production deploy so stack traces map to shipped code.
  • Healthchecks / uptime for scheduled jobs and critical endpoints.
  • Analytics / product signals only where it sharpens roadmap or bug triage.
  • Regression intake back into Linear so AI can pick them up as new work items.
Concern Early-stage default When to tighten it
Vercel Auto previews for PRs, auto prod on merge to main. If auth, billing, or user data risk grows, add protected environment or post-deploy smoke tests.
Railway Great for services, workers, APIs, cron-backed apps. Add health endpoints, migration discipline, and separate env vars by environment once state matters.
AWS Use only when you actually need its control surface. Prefer OIDC and least-privilege roles; otherwise secret sprawl gets ugly fast.
Sentry Mandatory from first production-ish launch. Tune alert noise and ownership as project complexity grows.
06

Recommended stack and policy set

Git policy
Protect main hard
Require PRs, required checks, conversation resolution, and preferably unique job names in workflows so GitHub doesn’t get weird.
Workflow policy
Treat workflows as prod infra
Minimal GITHUB_TOKEN perms, pinned actions where practical, no casual workflow rewrites by bots.
Delivery policy
Small PRs, fast loops
If a PR touches auth, payments, infra, data model, and UI all at once, split it. You’re not proving bravery; you’re making rollback impossible.
Area Recommended default Why
Issue tracking Linear Clean handoff point from product requirement to AI execution.
Default AI reviewer CodeRabbit Good always-on PR review surface without forcing three overlapping bots.
Invoked reviewers Codex + Claude Use on demand for risk-specific scrutiny or autonomous implementation tasks.
Required checks Lint, typecheck, tests, build, preview/smoke The minimum useful CI wall for AI-generated code.
Hosting Vercel / Railway first Faster loops, easier previews, less infra yak shaving.
Observability Sentry + uptime Production truth has to exist outside the PR conversation.
Merge mode Auto-merge after green checks Good fit for solo work once your gates are solid.
Branching Feature branch → PR → main The cleanest trunk-based model for a one-man shop.
07

30-day rollout plan

Week 1
Foundation
Protect main, set required checks, add preview deploys, wire Sentry, create repo instructions for AI reviewers.
Week 2
AI work loops
Linear → branch → PR automation. CodeRabbit always on. Codex/Claude comment triggers ready for specialist tasks.
Week 3–4
Tighten the machine
Add smoke tests on previews, release tags, regression-to-Linear loop, and manual prod approvals only if needed.
If you do only three things first: protect main, get previews on every PR, and install Sentry before the first real users show up. Those three buy you an absurd amount of sanity.
