01 · Research

What the Community Has Learned

The Consensus Pattern

From BetterClaw, ZenVanRiel, and X.com community discussions, the multi-agent playbook has converged on clear principles:

  • Workspace isolation is non-negotiable. Separate SOUL.md, MEMORY.md, memory/ directories. Shared memory between agents with different purposes creates context contamination — one user's research agent started citing its own speculative notes as sources.
  • Channel-per-agent routing via bindings is the simplest, most reliable pattern. Route specific Discord channels to specific agents. No proxy needed.
  • Start with one additional agent, not many. The "Dream Team" (14+ agents) approach creates coordination overhead that's rarely worth it. The sweet spot is 2-3 focused agents.
  • Hierarchical orchestration works best: One strategic agent (Opus) + specialized workers on cheaper models. This mirrors your existing pattern of Opus for synthesis, GPT-5.4 for cron jobs.
  • File-based handoffs > message queues for most personal setups. Shared directories with clear ownership beats infrastructure complexity.

What Works Well

  • OpenClaw's agents.list natively supports multiple agents with separate agentDir, model, tools, skills
  • bindings array routes channels to agents by channel ID, guild ID, or user
  • Cron jobs already have agentId field — reassignment is a one-line change
  • Memory isolation via separate workspace directories

Known Footguns

  • Skills that write to common paths create accidental shared state
  • Session binding confusion if bindings aren't explicit
  • No native agent-to-agent messaging (use shared files or sessions_send)
  • Context pollution if agents share the same MEMORY.md
02 · Analysis

Why Zosia Needs to Shed Weight

The Core Problem

Zosia is simultaneously your chief of staff, intelligence analyst, DevOps monitor, news editor, security auditor, and health coach. That works — but it creates three friction points:

  • Context window bloat. When you ask Zosia a quick question, she's carrying the overhead of 20+ skills, research pipelines, and monitoring instructions in her system prompt. That's expensive context on Opus.
  • Personality collision. The Reddit monitor's output voice ("📡 Reddit Pulse") has nothing in common with Zosia's personal assistant tone. They're wearing the same skin but doing fundamentally different jobs.

04 · Architecture

How the Two Agents Coexist

Single Gateway, Two Agents

Both agents run on the same OpenClaw gateway. No second process, no Docker, no extra infrastructure. The gateway's agents.list array holds both agent configs, and bindings routes channels to the right agent.

Zosia MAIN

  • Model: Opus (primary), full fallback chain
  • Workspace: ~/.openclaw/workspace (unchanged)
  • Channels: All DMs, all Discord channels except intel-specific ones
  • Tools: Full profile — browser, canvas, nodes, tts, voice, gateway, cron management
  • Identity: Chief of staff, personal advisor
  • Memory: Full MEMORY.md + distillation pipeline

Argus INTEL

  • Model: Opus (synthesis), GPT-5.4 (cron collection)
  • Workspace: ~/.openclaw/workspace-argus (new)
  • Channels: #reddit-gcc, #x-gcc, #daily-brief, #security, #development (Opik), #backups, #token-usage
  • Tools: Restricted — exec, web_fetch, memory_search, message only
  • Identity: Intelligence analyst, silent operator
  • Memory: Own MEMORY.md — operational state only, no personal context

Shared Resources (Read-Only)

Argus needs read access to some of Zosia's workspace for skill scripts and data directories. This is handled via symlinks or explicit paths in cron payloads — not shared workspace roots.

  • Skills scripts: Argus reads from ~/.openclaw/workspace/skills/*/scripts/ (existing Python pipelines). No need to duplicate — cron payloads already use absolute paths.
  • Data directories: Reddit/X monitor SQLite DBs stay in ~/.openclaw/workspace/skills/*/data/. Argus reads/writes these via exec — the agent workspace isolation is about memory and identity, not filesystem sandboxing.
  • Reports: Argus writes to ~/.openclaw/workspace/reports/ (shared output directory Zosia can reference if you ask about past reports).

Inter-Agent Communication

For your setup, agent-to-agent communication is minimal by design. Argus is autonomous — it collects, synthesizes, and posts to Discord. Zosia reads those posts naturally when you ask her about them. No message bus needed.

  • Argus → Zosia: Discord channel posts. If you ask Zosia "what did Reddit show today?", she reads #reddit-gcc.
  • Zosia → Argus: sessions_send if you ever need to trigger Argus interactively (rare).
  • Shared state: Reports directory + SQLite databases in skill data dirs.

06 · Configuration

The Actual Config Changes

Step 1: Create Argus Workspace

# New directory structure ~/.openclaw/workspace-argus/ ├── SOUL.md # Argus personality (intelligence analyst) ├── AGENTS.md # Agent instructions ├── MEMORY.md # Operational memory only ├── TOOLS.md # Tool reference for Argus ├── memory/ # Argus-specific daily notes └── config/ # Any Argus-specific config

Step 2: Add Argus to agents.list

// Added to agents.list array in openclaw.json { "id": "argus", "name": "Argus", "workspace": "~/.openclaw/workspace-argus", "model": { "primary": "anthropic/claude-opus-4-6", "fallbacks": ["openai-codex/gpt-5.4", "anthropic/claude-sonnet-4-6"] }, "identity": { "name": "Argus", "emoji": "👁️" }, "skills": [ "reddit-gcc-monitor", "x-gcc-monitor", "daily-brief", "token-usage-report", "opik-review-loop", "exa", "web-scraper", "doc-lookup" ], "tools": { "profile": "full", "alsoAllow": [ "read", "write", "edit", "exec", "process", "web_fetch", "memory_search", "memory_get", "image" ] } }

Note: Argus does NOT get gateway, cron, browser, canvas, nodes, tts, voice_call, or sessions_spawn. Those stay Zosia-only. Argus is a worker, not an admin.

Step 3: Add Channel Bindings

// Added to bindings array { "agentId": "argus", "match": { "channel": "discord", "channelId": "1470693532191953052" // #reddit-gcc } } // Repeat for: #x-gcc, #daily-brief, #security, #backups, #token-usage // Zosia's catch-all binding stays for everything else

Binding order matters. Specific bindings (Argus channels) must come before the catch-all (Zosia guild binding). First match wins.

Step 4: Update Cron Jobs

// For each migrating cron job, update agentId: cron update --jobId "466d1419-..." --patch { "agentId": "argus" } // Jobs already use absolute paths to scripts, so no path changes needed. // The cron payload messages reference skill paths explicitly.
06b · Personality

Argus SOUL.md — Draft

The Intelligence Analyst Persona

Unlike Zosia, Argus doesn't need charm, opinions, or personality. It needs precision, thoroughness, and signal clarity. Here's the personality framework:

  • Identity: Silent operator. Argus sees everything and reports what matters. No banter, no opinions on whether Raymond should care — just clean signal with evidence.
  • Voice: Terse, data-dense, structured. Headers, bullets, metrics. No prose unless the finding requires nuance.
  • Model preference: Always use the best available model for synthesis and analysis. Use cheaper models only for mechanical collection/classification tasks (already the pattern via cron model fields).
  • Output philosophy: "If it's not worth a bullet point, it's not worth mentioning." No padding, no summaries of summaries.
  • Error handling: Post failures immediately. Never silently fail. A one-line error card is better than silence.
  • Memory: Argus remembers operational state — what was last collected, pipeline health, recurring errors. Not personal context, not decisions, not preferences.
07 · Implementation Timeline

Build Sequence

Phase 1: Foundation LOW RISK

Create ~/.openclaw/workspace-argus/ with SOUL.md, AGENTS.md, MEMORY.md. Write the Argus personality. No config changes yet — just files.

Phase 2: Config + Test MEDIUM RISK

Add Argus to agents.list and create bindings. Restart gateway. Test that Zosia still works on all existing channels. Test that Argus responds in a test channel.

Phase 3: Migrate One Cron LOW RISK

Move the Token Usage Report to Argus first — it's the simplest cron, runs once daily, and is easy to verify. Watch one full cycle.

Phase 4: Migrate Research Crons MEDIUM RISK

Move Reddit + X monitors, Daily Brief, Opik Review. One at a time, one cycle each. These are the heaviest jobs — watch for path issues or skill access problems.

Phase 5: Migrate Ops Crons LOW RISK

Move backups, security review. These don't need skills — just exec + file access.

Phase 6: Tune & Observe ONGOING

Run both agents for a week. Check: Are all crons firing? Are bindings correct? Is Zosia's context lighter? Is Argus posting cleanly? Adjust as needed.

08 · Risks & Decisions

What Could Go Wrong

Skill Access

Argus needs to read skill scripts from Zosia's workspace. If agentDir isolation prevents this, cron payloads may fail. Mitigation: cron payloads already use absolute paths — they'll work regardless of workspace boundaries.

Message Tool Scope

Argus needs message tool to post to Discord. Verify that non-main agents can use the Discord message tool with the shared bot token. Mitigation: message tool is channel-level, not agent-level.

Memory Drift

If Argus encounters issues but can't write to Zosia's MEMORY.md, operational learnings might be lost. Mitigation: Argus maintains its own operational MEMORY.md for pipeline state.

Open Decisions for You

  • Name: Argus, or one of the alternatives above? This sets the tone for the agent's identity.
  • Heartbeat: Should Argus have its own heartbeat, or is cron-only execution enough? (I'd say no heartbeat — it's not conversational.)
  • Nightly distillation: Should Argus's operational memory get distilled too, or is it throwaway? (I'd say keep it simple — no distillation for Argus. Reset weekly.)
  • Interactive access: Should you be able to DM Argus directly, or is it cron-only? (I'd say cron-only to start. You can always add a channel binding later.)
  • Model for Argus crons: You want best models always. Keep Opus as Argus primary even for crons? Current pattern uses GPT-5.4 for crons — that's already the collection model, with Opus synthesis happening in the tier-2 prompts.

What Success Looks Like

  • Zosia's context is lighter — fewer skills loaded, fewer cron instructions in system prompt
  • All intelligence channels post on schedule with no regressions
  • Argus failures are isolated — a broken Reddit pipeline doesn't affect your morning DM with Zosia
  • You never notice the split — it just works
