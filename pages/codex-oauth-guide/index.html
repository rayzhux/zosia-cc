Codex OAuth — Keeping It Alive on Zosia & Zoe

A field guide to why your Codex tokens keep dying and how to stop it. Based on OpenAI's official docs, 50+ GitHub issues, X/Twitter community reports, and our own Mar 5 incident.

2026-03-26 · Research for Raymond

Why It Keeps Breaking

Root Cause Single-Use Refresh Tokens

OpenAI's OAuth refresh tokens are single-use. Once any process uses a refresh token, it's burned. If two processes (or two gateway restarts) try to refresh with the same token, the second one gets 401: refresh_token_reused. This is by design per OAuth spec — not a bug.

Bug 1: Token Not Persisted

OpenClaw's gateway refreshes the token in memory but may not write the new token back to auth-profiles.json before the next request loads the stale file. This is openclaw#52037 — confirmed across multiple VPS deployments.

Bug 2: Stale Session Cache

Even after codex mcp login succeeds, the running Codex session keeps using the old cached token. Requires a full session/gateway restart to pick up fresh creds. codex#14144

⚠️ auth.json is NOT safely portable across machines. Copying ~/.codex/auth.json to a second machine means two machines share the same refresh token. The first one to refresh burns it for the other. codex#15502 confirms this — the official docs are misleading.

Best Practices — Your Setup

Strategy The Golden Rule

Each machine gets its own independent OAuth session. Never share tokens between Zosia and Zoe. Each one logs in separately via device flow and maintains its own refresh cycle.

1. Use Device Flow Auth (Not auth.json Copy)

Since both Zosia (Mac) and Zoe (Hetzner VPS) are headless from your perspective, use the device code flow directly on each machine:

# On each machine separately:
codex login

# If headless, it will offer device code flow:
# "Visit https://auth.openai.com/codex/device and enter code: XXXX-XXXX"
# Complete in your browser, done.

Zosia has browser access (Mac), so standard OAuth works too. Zoe must use device flow.

2. Force File-Based Credential Storage

Make sure both machines store creds in files (not OS keyring), so the gateway can read them:

# In ~/.codex/config.toml on BOTH machines:
cli_auth_credentials_store = "file"

This ensures auth.json is the source of truth — critical for OpenClaw's auth-profiles sync.

3. Prevent Concurrent Refresh Races

The #1 killer. If multiple processes refresh the same token simultaneously, the second one burns it.

  • Single writer: Only one gateway process per machine should handle Codex auth
  • No concurrent crons: Space out Codex-dependent cron jobs so they don't all trigger refresh at once
  • Gateway restart = one refresh: After restart, the first API call refreshes; subsequent ones use the new token

4. Set Up Model Fallback Chains

This is your safety net. When Codex auth dies, the fallback model kicks in transparently:

# In OpenClaw config — set fallback for the codex provider:
# codex → sonnet (or gpt via API key)
# This way cron jobs and agents keep running even during auth outages

Multiple X users confirmed fallback chains saved them during silent token death across all gateways.

5. Proactive Token Health Monitoring

Don't wait for 401s. Check token health regularly:

# Check token expiry on each machine:
AUTH_FILE="${CODEX_HOME:-$HOME/.codex}/auth.json"
jq '{
  auth_mode,
  has_refresh_token: ((.tokens.refresh_token // "") != ""),
  last_refresh,
  expires_readable: (.tokens.expires_at | if . then (. / 1000 | strftime("%Y-%m-%d %H:%M UTC")) else "N/A" end)
}' "$AUTH_FILE"

Consider adding this to your heartbeat checks — flag when last_refresh is older than 5 days.

6. Quick Recovery Runbook

When it inevitably breaks (and it will, given the open bugs):

# Nuclear option — clean slate re-auth:
codex logout
rm -f ~/.codex/auth.json
codex login

# Then restart the OpenClaw gateway to pick up fresh tokens:
openclaw gateway restart
💡 Key insight from our Mar 5 incident: When multiple crons fail with 401 simultaneously, it's almost always the refresh token. Device flow re-auth takes ~2 min. Don't debug — just re-auth.

Gotchas to Watch For

  • OPENAI_API_KEY in environment — silently overrides OAuth. If set in .zshrc/.bashrc, Codex uses the API key instead of your OAuth session. unset OPENAI_API_KEY before running codex.
  • Multiple agents sharing one profile — If both Zosia-main and subagents use the same OAuth profile, a refresh race can occur. Keep one Codex OAuth profile per gateway.
  • VPN/proxy changes — Network changes can cause token exchange failures. If auth fails after a network change, restart the gateway.
  • openclaw models auth login --provider openai-codex hangs — Known bug on VPS. Use native codex login instead, then let OpenClaw sync from ~/.codex/auth.json.

TL;DR

Separate sessions per machine. Device flow auth on each. File-based cred storage. Fallback model chains. Monitor token age. Re-auth when stale — don't debug.

The underlying bugs (openclaw#52037, codex#14144, codex#15502) are still open. Until they're fixed, proactive re-auth every ~7 days is the safest play — especially on Zoe where you can't just walk up and fix it.
