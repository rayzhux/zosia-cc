02Architecture choices

There are three sane architectures. One is the practical default, one is the conservative baseline, and one is the "I want future portability more than convenience" option.

Recommended

A. Local Opik + OpenClaw plugin

Run Opik on the Mac with Docker/Colima. Install @opik/opik-openclaw in OpenClaw. Point plugin at local Opik API.

  • Best fit if you want deep traces with the least custom work.
  • Captures LLM spans, tool spans, sub-agent spans, cost, finalization.
  • Data stays local.
  • Tightest coupling to Opik, but still acceptable.
Best for: immediate value
Conservative

B. Built-in OpenTelemetry first

Enable OpenClaw's stock diagnostics-otel exporter now, defer Opik until later.

  • Lowest operational risk.
  • Good for metrics and health signals.
  • Not enough if you want rich agent trace debugging.
  • Useful as a baseline even if we do Opik later.
Best for: cautious rollout
Portable

C. OTel-centered architecture

Design around standard telemetry, then feed Opik / Langfuse / Phoenix downstream later.

  • Most future-proof.
  • Best if you expect to compare observability vendors.
  • More wiring, less instant gratification.
  • OpenClaw plugin-specific richness may still make Opik the first destination anyway.
Best for: avoiding vendor gravity
03How to decide the architecture

Pick based on what you care about most. Not vibes. Actual constraints.

If your priority is debugging OpenClaw behavior

Choose Option A. The official Opik plugin is the only path here that is obviously built around OpenClaw's native event model instead of making us fake it.

If your priority is minimum ops complexity

Choose Option B. Fewer moving parts, lower chance of container nonsense, but less useful for deep trace inspection.

If your priority is future vendor flexibility

Choose Option C. Standardize on telemetry collection first, then treat Opik as one backend rather than the architecture itself.

If your priority is privacy / local-only data

Choose Option A or C, both local. Avoid cloud-hosted observability unless you explicitly want remote access more than local control.

04Recommended design

My take: start with Option A, but keep the shape modular so it can evolve into Option C later. That means using Opik now for value, while avoiding stupid hard-coding decisions in naming, tagging, and rollout.

05Rollout plan

One phase at a time. Test after each step. No giant blind leap, because giant blind leaps are how weekends get ruined.

Phase 1 — runtime

Finish starting Colima, verify docker and docker compose actually work, and confirm local resource allocation is stable.

Phase 2 — Opik

Clone Opik repo, boot local stack, confirm UI loads, determine the correct local API endpoint for plugin config.

Phase 3 — OpenClaw plugin

Install plugin, patch gateway config carefully, restart gateway, verify plugin status and allowlist behavior.

Phase 4 — proof

Run one controlled test message, verify a full trace appears, then optionally enable stock OTel as secondary telemetry.

Exact execution sequence I’d follow

  • Bring up Colima and confirm Docker daemon socket exists.
  • Deploy Opik locally and capture its UI/API endpoints.
  • Install @opik/opik-openclaw.
  • Inspect gateway config subtree before edit.
  • Patch plugins.entries.opik-openclaw and plugins.allow.
  • Restart gateway.
  • Run openclaw opik status or equivalent status verification.
  • Send one test interaction and verify trace ingestion.
  • Only after that: decide whether to also enable diagnostics-otel.
06Risks, checkpoints, and rollback

None of this is scary if we respect checkpoints. It becomes scary when people "just keep going" after the first weird error.

Risk: container runtime flakiness.

Checkpoint: verify docker ps before touching OpenClaw. If Colima is unstable, stop right there and either fix runtime or fall back to Docker Desktop.

Risk: wrong Opik API endpoint.

Checkpoint: verify via Opik docs/runtime before config patch. UI port is not automatically the ingest URL. We should not guess and pray.

Risk: plugin loads but silently doesn't export.

Checkpoint: one controlled trace test immediately after install. If no trace lands, inspect logs before assuming "it probably works."

Rollback path.

Disable the plugin entry, remove it from allowlist if needed, restart gateway. Local Opik can stay running or be stopped independently.

My recommendation:

Do Option A now, but with one discipline rule: keep naming, tagging, and rollout structured enough that we can evolve toward an OTel-centered design later. That's the highest signal-to-effort move.
