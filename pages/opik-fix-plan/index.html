🔧 Opik Fix Plan — 3 Root Causes

Deep analysis + implementation plan · Mar 14, 2026
Architecture context: As of today, Argus (GPT-5.4 background agent) runs most cron jobs. Zosia (Opus interactive agent) handles conversations. Argus has browser in its tool deny list — it literally cannot use browser. The fixes below respect this split and modify shared skills + cron payloads accordingly.
Fix 1 — web_fetch speculative URL failures
Priority 1 · 44 errors / 6 days · 71% of web_fetch errors

Root Cause Deep Dive

The doc-lookup skill (v1.2.0) was already patched to stop guessing llms.txt URLs. That fix worked — but three deeper problems remain:

Problem A: No docs-cache in Argus's workspace

The doc-lookup skill writes cache files to docs-cache/ in the agent's workspace. Zosia's workspace has 28 cached entries. Argus's workspace has zero — no docs-cache/ directory exists at ~/.openclaw/workspace-argus/. Every Argus cron run that triggers doc-lookup starts from scratch and hits the same URLs that already failed for Zosia.

Problem B: Cron-spawned sub-agents don't inherit cache

When a cron job spawns as sessionTarget: "isolated", it gets the agent's workspace but may not read the cache directory proactively. The skill says "check cache first" but there's no enforcement — agents often skip to Step 2 (resolve canonical source) and probe URLs speculatively.

Problem C: The daily-brief pipeline hits blocked domains

The daily-brief skill already has a hardened blocked-domain list (Reuters, Bloomberg, FT, WSJ). But the Exa crawl fallback path still occasionally returns URLs from these domains, and the agent tries web_fetch on them before checking the blocklist. 5 of the 44 errors are this exact pattern.

Proposed Fix — 3 Steps

Implementation Plan

1

Create Argus docs-cache with Zosia's entries

Copy ~/.openclaw/workspace/docs-cache/ → ~/.openclaw/workspace-argus/docs-cache/. This gives Argus instant access to 28 verified entries. Future cron runs hit cache first instead of blind-probing.

Going forward, Argus will build its own cache naturally. Optionally, add a weekly sync script to copy Zosia's new cache entries → Argus.

2

Add a known-blocked-domains list to the doc-lookup skill

Create skills/doc-lookup/references/blocked-domains.txt with domains that consistently 404/403/401 (from the Opik data: Resend docs subdomain variants, Postmark API variants, paywalled news sites). The skill's Step 2 checks this list before making any fetch. If matched → skip and note it silently.

This is better than a verified-URL cache because it's a negative cache — we don't need to enumerate all good URLs, just avoid known-bad patterns.

3

Tighten doc-lookup SKILL.md retry behavior

Add a rule: "If web_fetch returns 401/403/404 on a URL, do not retry that exact URL or pattern in the same session. Log the failure silently and move to the next source in the ladder."

Also add: "For cron/isolated sessions: always read docs-cache/ before any network fetch. If the cache entry is <7 days old, use it and skip network entirely."

Expected Impact

~70% reduction in web_fetch errors. From 18% avg error rate → ~5%. The remaining 5% will be genuine first-time misses on new projects — which is normal and acceptable.

Argus Considerations

  • Argus has doc-lookup in its skills list — fixes to the skill SKILL.md affect both agents
  • The blocked-domains reference file lives in the shared managed skills dir, accessible to both
  • docs-cache is per-workspace (isolated), so Argus's cache won't pollute Zosia's
Fix 2 — Browser usage where APIs exist
Priority 2 · 35 errors / 4 days · Stale refs + timeouts

Root Cause Deep Dive

Where the 35 errors actually came from

  • Skill eval runs (Mar 9–10): 24 stale tab/target ID errors — these were Zosia (main agent) running skill-creator browser evals. Not a recurring cron problem.
  • Doc-lookup browser fallback (Mar 10–11): 6 element-not-found errors — Zosia used browser to read JS-rendered doc pages after web_fetch returned thin content.
  • Opik review (Mar 12–13): 5 UI action timeouts — agents trying to navigate Opik dashboard via browser instead of REST API. This is the only pattern that could recur in cron.

Critical insight: Argus already can't use browser

Argus has browser in its tool deny list. So the 5 Opik browser errors from Mar 12–13 were from before the Argus migration (those cron jobs ran under main agent at the time). Now that Opik review runs under Argus, browser is literally unavailable — that specific error source is already dead.

The remaining risk is Zosia's interactive sessions: doc-lookup and web-scraper can still fall back to browser when web_fetch returns thin content.

Proposed Fix — 2 Steps

Implementation Plan

1

Tighten doc-lookup's browser fallback language

Change Step 6 ("Deepen only if needed") from vague "use browser-based read only when necessary" to explicit criteria:

"Use browser ONLY when: (a) the content is confirmed JS-rendered AND (b) web_fetch returned <200 chars AND (c) Exa crawl also failed AND (d) the question genuinely requires that page's content. Always re-snapshot before acting on any browser element ref."

For cron/background contexts, add: "Never use browser. If web_fetch and Exa both fail, report the gap and move on."

2

No cron payload changes needed

All Argus cron jobs already explicitly ban browser or have it tool-denied. The opik-review-loop, daily-brief, and security review cron prompts all contain "do not use browser automation". These are already correct post-Argus migration.

For Zosia's interactive browser usage: the main risk is skill-creator eval runs (24 errors on Mar 9–10). These are legitimate uses — the fix is just to always re-snapshot before acting, which is already best practice. No skill change needed; just operational awareness.

Expected Impact

~90% reduction in browser errors for cron jobs (already achieved by Argus migration). For Zosia interactive: ~50% reduction by tightening doc-lookup's fallback criteria. Net: from 14% avg error rate → ~3%.

Surprising result: all 16 cron job channel targets are valid. Every channel ID in every cron payload maps to a real channel in the guild.

So where are the "unknown channel" errors coming from?

Two sources:

  • Argus Discord account context: Argus posts via the argus Discord account (separate bot token). When cron payloads say message(action=send, channel=discord, target=channel:XXXX), the message tool routes through the Argus bot token — which has requireMention: true and only a wildcard "*": { "allow": true } guild config. If the Argus bot hasn't been added to the guild with proper permissions, or if the message tool resolves accountId from bindings and picks the wrong one, you get "unknown channel".
  • Message action mismatches: The guildId required and query required errors happen when agents call message(action=search) or message(action=channel-info) without passing all required params. This is the agent constructing bad tool calls, not a config issue.
Proposed Fix — 3 Steps

Implementation Plan

1

Ensure Argus cron payloads specify accountId: "argus"

When Argus runs a cron job and calls message(action=send), it needs to explicitly pass accountId: "argus" so the message tool routes through the Argus bot token. Without this, the tool may default to the default account or fail to resolve the channel.

Add a line to each Argus cron payload prompt: "When posting to Discord, always pass accountId: 'argus' in the message tool call."

2

Add Discord channel reference to Argus TOOLS.md

Create a channel reference section in ~/.openclaw/workspace-argus/TOOLS.md listing all channels Argus posts to, with their IDs and names. This gives cron-spawned agents instant context without guessing.

3

Fix bad message tool call shapes in skill prompts

The guildId required and query required errors are from agents calling message(action=search) or message(action=member-info) without required params. Add a note to the Argus AGENTS.md: "When using the message tool: action=search requires query param; action=member-info requires userId param; action=channel-info requires channelId param."

Expected Impact

Eliminates the 8 "unknown channel" errors from Mar 14 and the 4 "required param" errors. Net: from 3.5% avg error rate → ~0.5%.

What we're deliberately not doing
  • Not changing models or cost structure — that's a separate initiative. The 92.5% GPT-5.4 cost concentration is real but it's by design (Argus runs on GPT-5.4 for context window reasons).
  • Not modifying gateway config — all fixes are workspace-level. Zero restart risk.
  • Not adding a verified-URL positive cache — the negative cache (blocked-domains) + existing docs-cache is sufficient. A positive cache would need constant maintenance.
  • Not removing browser from Zosia — browser is legitimately useful for interactive work (skill evals, JS-rendered pages, OAuth flows). The fix is tightening when it's used, not removing it.
