The Memory Palace:
A Personal Knowledge Graph for Everything

First-principles research into building a local-first, future-proof system that ingests every digital artifact in your life — meetings, emails, Slack, Notion, transcripts — and turns them into a queryable, interconnected knowledge graph on your MacBook.

First Principles

What are we actually building?

Before picking tools, let's decompose the problem. You want a system that does four things, each with fundamentally different technical requirements:

Ingestion

Collect everything, once

Pull data from 6+ sources (Gmail, Calendar, Slack, Notion, Granola, Discord) into a local canonical store. Incremental sync, not batch dumps. Dedup at the source level.

Extraction

Turn raw data into structured facts

LLM-powered entity extraction: people, companies, projects, decisions, action items, relationships. This is the expensive step — but you only do it once per document.

Storage

Store atoms + connections

Raw artifacts (emails, transcripts) AND extracted entities/relationships need to coexist. You need both vector search (semantic) and graph traversal (relational).

Retrieval

Answer any question across everything

Hybrid retrieval: keyword (BM25) + semantic (embeddings) + graph (multi-hop relationships). "What did Terence say about the AutoData pricing in the meeting after we discussed the Axxion deal?"

The Architecture Question

Graph database, vector store, or hybrid?

This is THE design decision. Here's my honest take after researching every option:

🎯 My recommendation: Hybrid — SQLite + Graph + Vectors in one local store

Not a graph database. Not a vector database. Both, embedded, in a single file. A pure graph DB (Neo4j) is overkill for a single-user personal system and adds operational complexity you don't need. A pure vector store (Qdrant, ChromaDB) misses relationships — you can't traverse "who introduced me to whom." The future-proof answer is a hybrid local store that gives you all three retrieval modes (keyword, semantic, graph) from one portable artifact.

Here's why, broken down by each approach:

Rejected

Pure Graph DB (Neo4j, FalkorDB)

  • Heavy — requires Docker/server even for local use
  • Neo4j is $36K/yr for enterprise; community edition is crippled
  • Great at relationships, terrible at semantic search
  • You'd still need a vector DB alongside it (Zep does this, costs $25-475/mo)
  • Operational burden for a single-user system is unjustifiable
Rejected

Pure Vector Store (ChromaDB, Qdrant)

  • Excellent at "find similar things" but blind to relationships
  • Can't answer "who did I meet through Amin?" — no graph traversal
  • Degrades with scale: 10K+ memories with no structure = noise
  • This is what basic RAG systems do — and it's not enough
Recommended

Hybrid Local Store

  • SQLite + sqlite-vec + graph tables in one .db file
  • BM25 (FTS5) for keyword, vectors for semantic, adjacency lists for graph
  • Zero ops: no Docker, no servers, no API keys for storage
  • Portable: one file you can backup, encrypt, restore
  • Proven at scale: 16K+ docs in 83MB (Blake Crosley's Obsidian retriever)
  • Future-proof: swap embedding models without changing storage

Recommended Architecture

The Memory Palace: a layered, local-first system

Four layers, each independently valuable, building on each other. You can ship Layer 1 in a week and get value immediately.

Layer 1 — The Lake

Local canonical copies of everything. Cron-synced raw artifacts from Gmail, Calendar, Slack, Notion, Granola, Discord. Stored as structured JSON/Markdown in ~/memory-palace/raw/. Deduplicated, timestamped. This alone is valuable — you never lose anything.

Layer 2 — The Index

Hybrid search over raw artifacts. SQLite with FTS5 (BM25) + sqlite-vec (semantic). Every artifact chunked, embedded (Model2Vec or OpenAI text-3-small), and indexed. Retrieval via Reciprocal Rank Fusion. Query anything by keyword or meaning.

Layer 3 — The Graph

Entities + relationships extracted by LLM. People, companies, projects, decisions, action items. Stored as graph tables in the same SQLite DB. Schema-enforced (nanograph philosophy). Enables: "Who was in the room when we decided X?" and "Map all my touchpoints with Company Y."

Layer 4 — The Brain

Synthesis + reasoning layer. GraphRAG-style retrieval: query hits vector + keyword + graph simultaneously. Context assembled and ranked. Mem0-style memory compression for frequently-accessed facts. This is where "super brain" questions get answered.

Concrete Tech Stack

What we'd actually build with

Storage Engine

  • SQLite — single file, zero ops, battle-tested
  • sqlite-vec — vector KNN search extension
  • FTS5 — built-in full-text with BM25
  • Graph via adjacency tables (entities, edges, properties)

Embeddings

  • Model2Vec (30MB, CPU, offline, fast) for bulk indexing
  • OpenAI text-embedding-3-small as quality fallback
  • Swap models freely — vectors are re-indexable

Entity Extraction

  • Claude / GPT for high-quality extraction
  • Schema: Person, Company, Project, Decision, Action, Meeting, Topic
  • Relationships: attended, decided, assigned, discussed, introduced
  • Run once per document, cache results

Ingestion Connectors

  • gog CLI — Gmail + Calendar (already have it)
  • Granola MCP / muesli — meeting transcripts
  • Notion API — via existing skill
  • Slack export / API — messages + threads
  • OpenClaw session logs — Discord + all channels

Retrieval

  • Hybrid BM25 + vector via RRF (k=60)
  • Graph traversal for relationship queries
  • Reranking with Cohere or cross-encoder
  • MCP server exposing tools to OpenClaw

Interface

  • OpenClaw skill (primary) — natural language queries
  • MCP server — tools for any LLM client
  • Obsidian vault (optional) — visual graph exploration
  • CLI for admin, debugging, and manual queries
Decisions Made

Why not just use Mem0 / Cognee / Neo4j?

Why not Mem0 self-hosted?

Requires Docker + PostgreSQL + Qdrant + OpenAI API key just to run. Graph memory requires their cloud ($249/mo). Their OSS version is vector-only. We'd inherit their architecture decisions and be locked into their update cycle. Better to borrow their extraction patterns and build leaner.

Why not Cognee?

Actually the closest to what we want. Their add → cognify → search pipeline is solid. But it's designed as a library for app developers, not a personal knowledge system. We could use it as a dependency or study its extraction pipeline. Worth revisiting as it matures. Top candidate for partial integration.

Why not Neo4j + Graphiti?

Graphiti's temporal knowledge graph is the gold standard for entity/relationship evolution. But it requires Neo4j (Java, JVM, 1GB+ RAM idle). For a single-user system on a MacBook, this is like using a forklift to move groceries. We can replicate the temporal patterns in SQLite graph tables.

The principle: For a single-user local system, operational simplicity beats feature richness. Every external dependency is a thing that can break at 3am. SQLite never breaks at 3am.

Implementation Roadmap

How we'd build this incrementally

Week 1-2: The Lake

Build ingestion crons for Gmail, Calendar, and Granola transcripts. Raw data lands as JSON/MD files in a structured directory. This alone gives you a searchable local mirror of your digital life.

Week 3-4: The Index

SQLite database with FTS5 + sqlite-vec. Chunk all raw artifacts, embed them, build the hybrid retrieval pipeline. Ship as an OpenClaw skill with a natural language query interface. This is already useful.

Week 5-6: The Graph

LLM-powered entity extraction pipeline. Define the schema (people, companies, projects, relationships). Process all historical data. Add graph tables to the same SQLite DB. Enable multi-hop queries.

Week 7-8: The Brain

Unified retrieval that fuses all three modes. Memory compression for hot facts. Meeting Intelligence becomes a thin layer on top. MCP server for external tool access. Obsidian export for visualization.

Each layer is independently valuable. You don't need the graph to get value from the index. You don't need the brain to get value from the graph. Ship and iterate — don't try to build the whole thing before getting any benefit.

Future-Proofing

What makes this last 5+ years

Embedding model independence

Store raw text alongside vectors. When better models emerge (they will), re-embed in hours. The graph structure is model-agnostic — entity relationships don't depend on embeddings.

LLM independence

Extraction runs offline against cached artifacts. Switch from Claude to GPT to Gemini to local models without re-ingesting. The extraction schema is the contract, not the model.

Data portability

One SQLite file + a directory of raw artifacts. No vendor lock-in. Export to any future system. The raw data is always there — you can re-process everything from scratch.

Composability

Meeting Intelligence is just a query pattern. Project tracking is a query pattern. People search is a query pattern. The knowledge graph is the foundation — applications are views.

Privacy by architecture

Everything on your MacBook. No cloud dependency for storage or retrieval. LLM calls for extraction can use local models if paranoia demands it. The system works offline.

Scalability path

SQLite handles 50K+ documents easily. If you outgrow it (years from now), the schema maps directly to PostgreSQL + pgvector + Apache AGE. Migration is a script, not a rewrite.

Steal From The Best

Patterns worth borrowing from each system

From Mem0

  • Two-phase memory pipeline: Extract → Update (ADD/UPDATE/DELETE/NOOP)
  • Memory compression — distill verbose transcripts into atomic facts
  • Conflict resolution: when facts contradict, the newer one wins (with audit trail)

From Zep/Graphiti

  • Temporal knowledge graph — facts have valid_from/valid_to timestamps
  • Episode-based ingestion — group facts by source event (meeting, email thread)
  • Custom entity types — model your specific domain (WAG subsidiaries, contacts)

From OMEGA + Blake Crosley

  • SQLite + sqlite-vec as the entire storage layer (proven at 16K+ files, 83MB)
  • Reciprocal Rank Fusion for hybrid search (BM25 + vector, k=60)
  • Model2Vec for CPU-speed local embeddings (30MB, no API calls)

From nanograph + Harper Reed

  • Schema-as-code: define entity/relationship types in a versioned schema file
  • Graph as a folder/file, not a service — copy, backup, version control
  • "Don't over-organize, just extract" — let the graph reveal structure
