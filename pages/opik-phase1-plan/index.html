OpenClaw × Opik · phase 1 only

Deterministic observability loop.
Zero browser nonsense.

Phase 1 is deliberately boring in the good way: pull signal from local Opik APIs and local OpenClaw logs, fingerprint recurring failures, separate real system problems from operator noise, and publish one clean daily review. No UI clicking. No auto-fix loop yet. No LLM-as-judge theatrics.

What Phase 1 does

  • Reads local Opik trace/span data for the last 24 hours.
  • Normalizes failures into stable fingerprints so repeats stop hiding in raw logs.
  • Classifies issues into actionable buckets: real bug, workflow noise, external noise, config mistake, cost anomaly.
  • Publishes a short operator review to #development and saves markdown + JSON snapshots locally.

What Phase 1 explicitly does not do

  • No browser automation against Opik.
  • No silent config mutations or automatic remediation.
  • No complex evaluation rules inside Opik yet.
  • No pretending every error is a platform bug when half of it is us using tools stupidly.

01

Objective

Build a trustworthy feedback loop from observability into operations. The point is not "collect more telemetry"; the point is to make recurring failures obvious enough that we can decide whether to fix, suppress, replace, or redesign the noisy part of the system.

Primary outcome

One daily operator-grade answer

Every morning, OpenClaw should be able to say: what broke, what repeated, what cost looked weird, and what deserves fixing next.

Design principle

Deterministic first, smart second

Phase 1 uses stable API queries, local scripts, and explicit rules. If the foundation is sloppy, adding more AI just automates the slop faster.

02

Inputs and sources of truth

Everything comes from local deployment surfaces we control. If the UI and the APIs disagree, the APIs win. If memory notes disagree with runtime evidence, runtime wins again.

Opik API

Primary telemetry surface

  • /v1/private/projects to resolve project identity
  • /v1/private/traces/search for raw run-level evidence
  • /v1/private/spans/search for tool/LLM failure detail
  • /v1/private/traces/stats and /v1/private/spans/stats for summary checks
  • /v1/private/projects/{id}/metrics for cost / token / count trends
OpenClaw runtime

Secondary corroboration

  • openclaw status for gateway/session health
  • Plugin/runtime warnings from local logs
  • Current Opik exporter status and config sanity
  • Saved daily markdown + JSON review snapshots for recurrence detection
Out of scope

Ignored on purpose

  • Any browser-driven Opik workflow
  • Cloud-only helper features like single-trace AI debugging
  • Manual visual inspection as a dependency for the loop
  • "Maybe the UI showed something" as an evidence source
03

Daily pipeline

The first phase loop is six deterministic steps. Simple enough to trust, rich enough to be useful.

1
Collect

Pull 24h data

Query project, traces, spans, and core metrics for the last day from local Opik.

2
Normalize

Fingerprint errors

Collapse raw messages into stable families like missing binary, stale target, config patch misuse, or bad fetch URL.

3
Aggregate

Compute pressure

Count frequency, error rate, duration drag, token cost, and top noisy tools/workflows.

4
Classify

Separate noise from bugs

Tag each fingerprint as real platform issue, workflow misuse, external/docs noise, config mistake, or anomaly.

5
Persist

Save evidence

Write reports/opik-daily/YYYY-MM-DD.md and snapshot JSON for trend comparison.

6
Publish

Post operator review

Send one concise daily note to #development with what happened and what deserves fixing next.

04

Classification model

This is the heart of the loop. If we fail to classify correctly, the report becomes another noisy dashboard nobody trusts.

Bucket What it means Examples Expected action
Real system issue Something in OpenClaw, plugin plumbing, or runtime behavior is actually unreliable. Exporter failures, repeated trace write failures, broken local integration paths. Escalate in report; investigate or patch.
Workflow / operator noise The system is mostly fine, but the calling pattern is dumb or fragile. Stale browser tabs, missing rg, wrong tool assumptions. Fix prompts, wrappers, defaults, or tool choice.
External / docs noise Bad URLs, flaky docs fetches, or third-party weirdness muddying signal. Repeated web_fetch 404/401 against guessed pages. Cache verified URLs, tighten lookup path.
Config workflow mistake The operation failed because config editing discipline was sloppy. Bad schema path, malformed patch payload, invalid config patch attempt. Codify safer config edit workflow.
Cost / usage anomaly Behavior may be correct, but spend or token burn looks off. Sudden token spike, expensive loop, overlong retries. Flag for human review; no auto-action in phase 1.
Rule: Phase 1 should be blunt. If a failure is mostly self-inflicted workflow churn, say that plainly instead of dressing it up as a platform incident.
05

Outputs

Three outputs, all useful. If one of them disappears, the loop gets weaker fast.

Markdown report

Human-readable daily review

Stored under reports/opik-daily/. This is the operator narrative: snapshot, noisy tools, error fingerprints, and suggested fixes.

Snapshot JSON

Machine-comparable evidence

Stored under reports/opik-daily/snapshots/. Used to detect recurrence across days without scraping chat history or guessing.

Discord note

Short daily brief

Posted to #development. Keeps the loop visible without forcing anyone to open raw traces just to know what sucked today.

06

Guardrails and non-goals

This phase should diagnose and prioritize — not become a self-editing monster.

Guardrails
  • No browser automation anywhere in the loop.
  • No silent config changes, tool disables, or gateway restarts.
  • No dependence on cloud-only Opik helper features.
  • No broad claims without saved evidence in the daily snapshot.
Deferred to later phases
  • Auto-remediation queue with apply-ready patches
  • Weekly trend digest and escalation scoring
  • Rule registry for suppress / ignore / replace decisions
  • Opik evaluator rules for richer online analysis
07

Success criteria

If Phase 1 works, we’ll know because the loop becomes boringly reliable and the recommendations stop feeling hand-wavy.

1

Daily report lands reliably at the same time with zero browser involvement.

2

Recurring fingerprints become obvious across days instead of showing up as isolated one-offs.

3

The report cleanly distinguishes platform faults from operator/tooling stupidity.

4

By the end of a week, we can name the top 3 system improvements with evidence instead of vibes.
