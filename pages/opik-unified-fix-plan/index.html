Root cause: Both bots receive every guild message

Both Discord bot tokens (Zosia default + Argus argus) are connected to the same guild. When Raymond posts a message, both bots receive the Discord message event simultaneously. The gateway routing is:

  • Default bot receives message → binding matches guildId: 1467953146176213097 → routes to main (Zosia) → ✅ correct
  • Argus bot receives message → despite requireMention: true, it still processes it → routes to argus → ❌ unintended

The requireMention: true setting on the Argus account is not preventing Argus from responding. This is either a bug in how the binding/mention filter interacts with the wildcard channel config, or the binding { accountId: "argus" } bypasses mention filtering.

The flood: Argus streams narration as separate Discord messages

Even if Argus only responded once, the way it responded is a UX disaster. It sent 15+ fragmented messages in 16 seconds:

  • "I'm checking the current runtime…"
  • "Now I'm pulling the local evidence…"
  • "I've got the current config and channel map…"
  • "I'm narrowing the browser audit…"
  • Then 11+ messages of analysis, each a paragraph fragment

This is streaming: "partial" combined with Argus narrating its tool calls instead of just doing them silently. The system prompt says "Never output internal reasoning/planning. Final answer only." but Argus isn't following it for intermediate steps.

Fix — Immediate

Stop Argus from responding to channel messages

Argus is a background pipeline agent. It should never respond to channel messages — only to cron triggers and sessions_send from Zosia. Two options:

Option A: Remove the Argus binding entirely (recommended)

Delete the binding { agentId: "argus", match: { channel: "discord", accountId: "argus" } }. Argus cron jobs use delivery.mode: "announce" with explicit channel targets — they don't need an inbound binding to post.

{
  "bindings": [
    { "agentId": "main", "match": { "channel": "discord", "guildId": "1467953146176213097" } }
    // Argus binding removed — cron delivery handles outbound
  ]
}

Risk: Low. Argus cron jobs post via delivery announcements, not via inbound message routing. Need to verify cron delivery still works without a binding — test one cron job manually after the change.

Option B: Restrict Argus to only its output channels

If we need Argus to sometimes receive messages (e.g., someone @Argus in a channel), change the wildcard to an explicit channel list with requireMention: true enforced:

"guilds": {
  "1467953146176213097": {
    "requireMention": true,
    "channels": {
      "1467962275481522380": { "allow": true },  // #daily-news
      "1467958004811829318": { "allow": true },  // #token-usage
      "1468180617262010532": { "allow": true },  // #backups
      "1467971312923181151": { "allow": true },  // #development
      "1470693532191953052": { "allow": true },  // #reddit
      "1470710407852462091": { "allow": true },  // #x-gcc
      "1480919048891142205": { "allow": true }   // #security
    }
  }
}

Risk: Low. But if requireMention is genuinely broken at the binding level, this won't help either — Option A is safer.

Recommendation: Go with Option A. Argus is a pipeline agent — it has no business responding to channel messages. Cron delivery handles all its output. If someone needs to talk to Argus, Zosia can relay via sessions_send. This eliminates the dual-response problem entirely.

Fix 1 — web_fetch speculative URL failures (44 errors / 6 days)
Skill + Cache Changes · No restart

Shared docs-home cache + fetch policy enforcement

Both agents agree: The doc-lookup skill text is already improved, but agents still speculate at runtime. The fix is enforcement, not more instructions.

Copy Zosia's docs-cache to Argus

cp -r ~/.openclaw/workspace/docs-cache/ ~/.openclaw/workspace-argus/docs-cache/

Gives Argus instant access to 28 verified entries. Eliminates cold-start probing on every cron run.

2

Create a shared docs-home registry (Argus's suggestion)

A JSON file mapping product → canonical docs root. Agents check this BEFORE any fetch. Prevents speculative subdomain guessing.

  "openai": "https://platform.openai.com/docs",
  "discord": "https://discord.com/developers/docs",

  "resend": "https://resend.com/docs",
  ...

3

Add a blocked-domains list (Zosia's suggestion)

A negative cache for domains that consistently 404/403/401. Prevents retrying known-bad URLs.

// skills/doc-lookup/references/blocked-domains.txt
# Paywalled / bot-blocking news sites
usnews.com
aawsat.com
reuters.com
bloomberg.com

# Known bad doc subdomains

4

Tighten SKILL.md with hard rules (merged from both)

  • Check docs-registry.json first. If product found → use that root, skip guessing.
  • If web_fetch returns 401/403/404 → do NOT retry that URL or domain variant in the same session.
  • For cron/isolated sessions → always read docs-cache/ before any network fetch. If cache <7 days old → use it.
  • No llms.txt probing unless explicitly justified.
  • Subagents doing doc work must inherit the same rules (add to task prompts).

Expected impact: 18% avg error rate → ~4%. Eliminates ~70% of web_fetch errors.

Fix 3 — Discord channel targeting (18 errors / 4 days)
Config + Workspace Changes · No restart

Channel registry + identifier hygiene

Both agents confirmed: All 16 active cron target channel IDs are valid. The errors come from agents confusing guild IDs with channel IDs, and from bad message tool call shapes.

Argus found a smoking gun

Agents are using the guild ID 1467953146176213097 where a channel ID is required. Discord returns "Unknown Channel" because that's not a channel — it's the guild.

1

Create a machine-readable channel registry (Argus's suggestion)

Generate from message channel-list and store in both workspaces. Includes channel ID, name, type, parent, and whether components are allowed.

// config/discord-channels.json
{
  "guild": "1467953146176213097",
  "channels": {
    "1467962275481522380": { "name": "📰-daily-news", "type": "text" },
    "1467958004811829318": { "name": "📊-token-usage", "type": "text" },
    ...
  }
}
2

Add channel reference to Argus TOOLS.md

Give Argus's cron sessions instant context about available channels, their IDs, and supported actions. Prevents guild-vs-channel confusion.

3

Add message tool param guidance to Argus AGENTS.md

"When using message tool: action=search requires query. action=member-info requires userId. action=channel-info requires channelId. Never pass guild ID where channel ID is expected."

4

Clean up dead cron reference (Argus found)

The disabled CF Crawl Endpoint Retest job references channel 1481209726351052820 which doesn't exist. Remove it.

Expected impact: 3.5% avg error rate → ~0.5%.
