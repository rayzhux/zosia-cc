Why BGE-M3 wins for your use case

  • Bilingual excellence — trained extensively on Chinese corpora by Beijing Academy of AI. MIRACL score 69.2 (best in class for multilingual retrieval)
  • Hybrid retrieval built-in — dense + sparse vectors simultaneously, better recall for memory search
  • 1024 dimensions — sweet spot for quality vs storage. 100K memories = ~400MB vectors
  • Tiny footprint — 568M params, ~2.3GB RAM. Leaves 21GB for everything else
  • Native Mem0 support — one-liner config via Ollama provider

Voyage-4 asymmetric embedding (future upgrade)

Unique innovation: all voyage-4 models share a single embedding space. Embed documents with voyage-4-large ($0.12/M) once, then query with voyage-4-nano (free) at runtime. First vendor to offer this — perfect for a memory system where corpus is static but queries are dynamic.

Why not one model for everything?

The tiered approach isn't about cost — it's about matching quality to importance. A casual email to a vendor doesn't need Sonnet-level extraction. A strategic meeting with your chairman does. Mem0 supports per-instance LLM switching, so this is trivial to implement: tag documents by source/importance, route to the appropriate model.

Structured output is critical: Mem0's extraction pipeline requires clean JSON with ADD/UPDATE/DELETE/NOOP operations. GPT-4.1-mini and Claude both excel at this. Local Qwen3-14B requires careful prompting but handles it well in thinking mode.

Neo4j CE — Why it wins

  • Mem0's default graph backend — best documented path, zero adapter work
  • Full Cypher — most mature query language, best tooling, most LangChain/LlamaIndex integrations
  • No Docker — native macOS install via brew install neo4j
  • Graph algorithms — GDS library for PageRank, community detection, shortest path, centrality
  • Full-text search — native Lucene-based FTS built in
  • Active project — 14K+ GitHub stars, continuous development, massive community
  • Upgrade path — if you outgrow local, Neo4j AuraDB cloud is one config change in Mem0

Neo4j CE — Trade-offs

  • JVM overhead — 2–4GB RAM baseline (heap + page cache). Configured via neo4j.conf
  • Cold start — ~10–15 seconds to start (JVM warmup). Not an issue for always-on service
  • No hot backups in CE — must stop DB or use neo4j-admin database dump
  • Single node only in CE — no clustering (fine for personal use)
  • Slower than Memgraph/FalkorDB on raw traversal — but 5–50ms for 3-hop on 100K nodes is more than adequate
Decision: Neo4j Community Edition via Homebrew — the only remaining option that's (a) natively supported by Mem0, (b) actively maintained, (c) Docker-free on macOS, and (d) has a full Cypher implementation. The 2–4GB RAM overhead is the main cost — moves total usage from ~10GB to ~12.5GB in normal operation, still leaving ~11.5GB free on your 24GB M2. Configure heap to 2GB and page cache to 1GB for personal-scale data.

Alternative: If you ever want maximum graph performance and don't mind Docker, Memgraph is 3–10x faster with full Cypher and native Mem0 support. Keep it as a future option.

When cloud is justified (the extraction LLM case)

The extraction LLM is the only component where cloud APIs are justified, and only for specific scenarios:

  • Real-time daily ingestion — fresh emails/transcripts benefit from Sonnet/Haiku's superior nuance on ambiguous entity mentions, coreference resolution, and relationship inference
  • High-value documents — meetings with Terry, Amin, Wang Shaofeng get Sonnet-level extraction because getting relationships wrong here has real business impact
  • Cost is negligible — even Sonnet at $3/$15 per million tokens costs ~$0.68/day for 50 documents. Not a factor.

But batch backfill should go local: Processing 5K+ historical documents through cloud APIs exposes your entire email/meeting history. Qwen3-14B locally gets ~85% of cloud quality — good enough for historical data that's primarily building context, not driving decisions.

Reliability: What happens when APIs are down?

With v2's architecture, the answer is: almost nothing breaks.

  • Search always works — embeddings (local), vector search (local), graph traversal (local), reranking (local) are all on-device
  • New memory extraction degrades gracefully — if cloud LLM is down, fall back to local Qwen3-14B. Queue documents for re-extraction when cloud returns.
  • Works on a plane — fully functional offline except for new memory extraction (and even that works with local fallback)

12 Updated Roadmap

Phase 1 — Foundation (Week 1)

  • Install Neo4j CE (brew install neo4j), Qdrant (brew install qdrant), Mem0 OSS (pip install "mem0ai[graph]")
  • Pull BGE-M3 and Qwen3-14B via Ollama
  • Write custom extraction prompt tuned for your entity schema (people, companies, projects, decisions, action items)
  • Set up the FastAPI REST server on port 8200
  • Test with manual .add() and .search() calls — verify graph+vector dual storage works
  • Install BGE-reranker-v2-gemma via FlagEmbedding, integrate as post-search step

Deps: Python 3.10+, Java 21+ (for Neo4j), Ollama, Homebrew. No Docker.

Phase 2 — Ingestion Pipeline (Week 2–3)

  • Build Python ingestion scripts for Gmail (both accounts), Calendar (both accounts), Granola transcripts
  • Implement tiered LLM routing: tag documents by source/importance → route to appropriate model
  • Historical backfill via local Qwen3-14B (privacy) or GPT-4.1-mini batch API (speed)
  • Each script is idempotent with processed-document tracking
  • Add fallback: if cloud LLM fails, auto-queue for local extraction

Phase 3 — OpenClaw Skill (Week 3–4)

  • Build memory-palace OpenClaw skill wrapping the REST API
  • Natural language queries: hybrid vector + graph retrieval + reranking pipeline
  • Refactor Meeting Intelligence to query the palace instead of live-fetching everything
  • MCP server for coding agents (Claude Code, Codex) to access the palace

Phase 4 — Full Ingestion (Week 4–5)

  • Add Notion, Slack, OpenClaw session logs, WhatsApp/Telegram archives
  • Nightly cron for incremental sync of all sources
  • Ingestion dashboard (memory count, entity count, relationship count, last sync)

Phase 5 — Intelligence Layer (Week 6+)

  • Advanced graph queries: relationship chains, temporal patterns, network analysis
  • Memory compression for frequently accessed facts
  • Backup to R2 via existing nightly backup cron
  • Optional: upgrade embeddings to voyage-4-large for absolute SOTA quality
  • Optional: Obsidian export for visual graph exploration

What stays the same from v1

  • All data sources (Gmail, Calendar, Granola, Notion, Slack, sessions, WhatsApp/Telegram)
  • Entity schema (Person, Company, Project, Meeting, Decision, ActionItem, Topic, Location)
  • Relationship types (WORKS_AT, REPORTS_TO, ATTENDED, DECIDED, etc.)
  • OpenClaw integration pattern (skill + MCP + REST API)
  • Existing OpenClaw infrastructure (gateway, crons, MEMORY.md, Argus)
  • Backup strategy (R2 snapshots)
